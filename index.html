Testing summary

Accessibility and performance testing

Created November 7, 2026 Updated November 9, 2026

Executive summary

The landing page scores 100 for performance and 100 for accessibility in Google Lighthouse, on both a simulated mid-range phone and desktop. The first audit, on the prototype, scored 58 for performance. We also tested against WCAG 2.2 AA, the newest accessibility standard, with tools, scripts and real key presses, and found no failures. These tools are diagnostic, and the scores come with no design choices given up.

Bottom line

The page passes every automated and scripted test we ran. We can't claim WCAG conformance until people test it with screen readers.

What changed and what varies

  • 58 to 100

    The production build sends only the code and styles the page uses, minified, with WebP images. Downloads fell from about 730KB to 191KB.

  • 95 to 100

    The English score moves between runs because the page waits for the temporary Google font. The City's own font file should keep it at 100.

  • Phone first

    The phone test is the hard one: a slowed processor and a slow connection. Desktop uses a fast connection and no slowdown, so it scores the same or higher. Tablet is covered in the next section.

  • React 97

    Typical of three runs; one slower run scored 94 (2.6s). The gap to 100 has two causes. The temporary Google font blocks the first paint for about 0.8s, which self-hosting the fonts fixes for both builds. And nothing shows until React's code loads, which pre-rendering the page to HTML in the real build fixes.

  • Legible text

    The phone demo's words measured about 7px on a phone, so Lighthouse counted half the page's text as too small. The demo is now laid out at full size, with 16px text, and scaled down as one picture. It looks the same, and Best practices went from 96 to 100.

  • React SEO

    The React app had no page description, and its server answered robots.txt with a web page. It now has both: the description follows the page's language. SEO went from 83 to 100.

03

Standards and targets

The standards are public. The targets are our own choice, set above each standard's pass mark.

  • WCAG 2.2 AA

    The accessibility standard US law refers to. The ADA's 2024 rule requires state and local governments to meet WCAG 2.1 AA; version 2.2 includes all of 2.1 and adds more.

  • Core Web Vitals

    Google's measure of how fast a page feels, used across the industry: the largest thing on screen drawn within 2.5s, content that doesn't jump, and a page that responds to input within 200ms.

  • Performance 95+

    Lighthouse calls 90 good. We aimed higher to leave room for a real host, the video and later additions, and because many New Yorkers use older phones on slower connections.

  • Accessibility 100

    No automated failure at all. It is a public service page for everyone, and automated failures are the easiest problems to prevent.

How the performance score works

Lighthouse imitates a mid-range Android phone: a processor slowed four times, a slow 4G connection (150ms delay, about 1.6 Mbps) and a 412 by 823 screen. Each measurement is graded against millions of real websites, and the score combines them by weight.

05

Tools and methods

Lighthouse covers only part of WCAG, so most accessibility testing went beyond it.

  • Lighthouse 12

    Google's tester, in mobile mode, for the performance score and a subset of accessibility checks.

  • Clean runs

    Every score here comes from a browser with no extensions: the command line or an Incognito window. Extensions add their own scripts and errors to the report; in one run they inflated unused JavaScript from 42 KiB to 1,175 KiB.

  • axe-core

    Deque's accessibility tester, which most tools are built on. The full WCAG 2.2 AA rule set, at 320, 375, 800, 1024 and 1280px.

  • Keyboard

    Real Tab and Shift+Tab presses through the whole page. Every stop shows a focus ring, the order matches the reading order, nothing traps focus, and the sticky header never hides it.

  • Measurement

    Scripts for contrast (lowest text 4.68:1, against 4.5:1 required), no sideways scrolling at 320px or 400% zoom, doubled text spacing and 200% text.

  • Text zoom

    Safari's text-only zoom at every step up to 300%, at seven widths from 320 to 1920px.

  • npm run check

    Runs on every build, in all 11 languages: layout at eight widths, keyboard pausing the animations, reduced motion, enlarged text and screen reader announcements.

06

How we read the scores

Lighthouse, axe and the other tools are diagnostic. They find problems; they don't define a good site. A good site balances technical health with the emotional and visual impact its audience needs.

  • Diagnostic

    We use the scores to find and fix problems, not as the goal. We don't chase a number for its own sake.

  • Perceived speed

    A page can be objectively faster, and score better, yet feel worse to a person. Motion, pacing and how content appears are designed for how the page feels, not only for how it measures.

  • No trade-off

    The high scores come with every design choice intact: the hero animation, the How it works media, the type and the illustrations. Nothing was cut or simplified to raise a score, so the page stays strong, clear, simple and elegant for New Yorkers.

07

Limits and what's left

What these numbers don't show, and what needs a person before launch.

  • Automated

    A score of 100 means no automated check failed. Automated tools find roughly a third to a half of real accessibility problems.

  • Lab data

    One imitated phone on a local server. Real visitors' speed can only be measured after launch.

  • Screen readers

    VoiceOver on Mac and iPhone, NVDA on Windows, TalkBack on Android, and JAWS if OTI requires it.

  • Still to test

    Text zoom in Firefox, OTI's requirements that may be relevant, and a final run on the real host once the footer and FAQ answers are in.
